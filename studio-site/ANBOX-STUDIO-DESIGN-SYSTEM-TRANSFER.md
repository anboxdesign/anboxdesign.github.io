# ANBOX Studio Core — полный файл дизайн-системы для переноса

Статус: `core/current`  
Версия: `2026-08-06`  
Область: основная дизайн-система ANBOX Studio и база для всех направлений  
Назначение: самостоятельный handoff-файл для переноса в другую задачу, проект, workspace или агентную сессию

---

## 1. Как использовать этот файл

Этот документ является самодостаточным описанием ANBOX Studio Core. При переносе его нужно передать принимающему дизайнеру, разработчику или агенту целиком до начала работы.

Правила приоритета:

1. текущая задача и прямые указания пользователя;
2. этот файл;
3. локальная спецификация активного направления;
4. макеты, референсы и research-документы;
5. архивные итерации только как история, но не как требования.

Если локальное направление переопределяет Core, оно обязано явно назвать:

- какое правило изменяется;
- почему изменение необходимо продукту;
- где действует отклонение;
- какой fallback используется;
- что продолжает наследоваться от Studio Core.

## 2. Главный контекст

ANBOX Studio — первичная студийная система. Она объединяет:

- основной бренд и коммерческий сайт;
- клиентскую студийную практику;
- `ANBOX Slides`;
- `ANBOX Study`;
- `ANBOX Live Tuner`;
- motion-библиотеку;
- дизайн-системы, transfer kits, QA и автоматизацию;
- визуальный, контентный и видео-продакшен.

Studio Core первичен. Направления наследуют его базовую грамматику, но не обязаны выглядеть одинаково.

ANBOX нельзя описывать только через презентации, курсы, Tilda или один визуальный приём. Это экосистема студии с общей дисциплиной и самостоятельными продуктовыми ветками.

## 3. Суть дизайн-системы

ANBOX выглядит как студия, которая проектирует системы, а не как набор сайтов, собранных из одного шаблона.

Единство создают:

- характерный кириллический display в H1 HERO и Onest на всей остальной странице;
- строгая сеточная дисциплина;
- ясный интерфейсный текст;
- case-led композиция;
- реальные работы и материальные визуалы;
- точные контрастные сигналы;
- общий брендовый уровень `ANBOX STUDIO`;
- содержательная интерактивность;
- качественная адаптация, доступность и проверка на реальных устройствах.

Различие направлений создают:

- продукт и аудитория;
- бизнес-модель;
- реальные кейсы;
- локальная палитра;
- собственная композиция hero и секций;
- motion-бюджет;
- CTA и воронка;
- способ доставки.

Короткая формула:

```text
Studio Core = сетка + типографика + бренд + case-led подход + production quality
Direction = Studio Core + собственная продуктовая арт-дирекция
```

## 4. Визуальный характер

Система должна передавать:

- независимую современную дизайн-студию;
- профессиональную уверенность без корпоративной тяжести;
- экспериментальность, удерживаемую сеткой;
- физичность и материальность дизайна;
- ясность и прямоту коммуникации;
- способность работать с разными типами продукта;
- ощущение живой практики, а не готового шаблона.

Система не должна выглядеть как:

- универсальный SaaS-лендинг;
- массовая онлайн-школа;
- галерея одинаковых скруглённых карточек;
- набор случайных трендовых эффектов;
- презентация, растянутая на веб-страницу;
- тёмный WebGL-demo без ясного продукта;
- маркетплейс услуг без авторского характера.

## 5. Базовая геометрия

### 5.1. Core tokens

```css
:root {
  --abx-studio-shell: 1200px;
  --abx-studio-gutter: 20px;
  --abx-studio-grid-gap: 20px;
}
```

### 5.2. Основной shell

```css
.abx-studio-shell {
  width: min(
    var(--abx-studio-shell),
    calc(100% - var(--abx-studio-gutter) * 2)
  );
  margin-inline: auto;
}
```

### 5.3. Основная сетка

```css
.abx-studio-grid {
  display: grid;
  grid-template-columns: repeat(12, minmax(0, 1fr));
  gap: var(--abx-studio-grid-gap);
}
```

### 5.4. Принципы компоновки

- Desktop shell: `1200px`.
- Базовый gutter: `20px`.
- Базовый column gap: `20px`.
- Основная сетка: 12 колонок.
- Секции имеют свободную высоту по содержимому.
- Hero может быть крупным, но не должен ощущаться изолированным слайдом.
- Желательно показывать продолжение страницы или ясный маршрут скролла.
- Асимметрия разрешена, если она остаётся привязанной к сетке.
- Кейс или материальный объект может сознательно выходить за внутреннюю текстовую колонку.
- Основной контент не должен получать горизонтальный скролл.
- Фиксированные карточки `1560 × 700` не относятся к Studio Core.

### 5.5. Adaptive

На tablet и mobile композиция пересобирается, а не механически уменьшается.

Обязательные правила:

- текстовая и визуальная иерархия сохраняется;
- элементы не зависят только от hover;
- крупный display проверяется отдельно на `1440`, `390` и `320px`;
- реальные кейсы не теряют главный объект при crop;
- CTA остаётся видимым и доступным;
- touch targets имеют достаточный размер;
- важная информация не прячется в горизонтальной карусели без альтернативы.

Рабочий adaptive token:

```css
@media (max-width: 980px) {
  :root {
    --abx-studio-gutter: 16px;
  }
}

@media (max-width: 720px) {
  :root {
    --abx-studio-gutter: 12px;
  }
}
```

Локальное направление может назначить другие mobile gutters после визуальной проверки.

## 6. Типографика

### 6.1. Display HERO

Подтверждённый студийный display-файл:

```text
bebas-neue-bold.woff
```

Рекомендуемое подключение:

```css
@font-face {
  font-family: "ANBOX Display";
  src: url("FONT_PATH/bebas-neue-bold.woff") format("woff");
  font-weight: 700;
  font-style: normal;
  font-display: swap;
}
```

Использование:

- только H1 внутри HERO;
- uppercase-кириллица;
- плотная главная композиционная фраза первого экрана.

Ограничения:

- не использовать для длинного текста;
- не использовать как основной UI-шрифт;
- не использовать для H2–H6, названий секций, карточек, кейсов и перебивок;
- не применять автоматически к CTA, датам, ценам и латинице;
- не подменять публичным `Bebas Neue Regular`;
- не называть Evolventa точным студийным display-файлом;
- проверять фактически загруженный файл без системного fallback.

### 6.2. Основной текст и UI

```css
:root {
  --abx-font-hero-display: "ANBOX Display", "Arial Narrow", Arial, sans-serif;
  --abx-font-heading: "Onest", Arial, sans-serif;
  --abx-font-ui: "Onest", Arial, sans-serif;
}
```

Onest используется для:

- всех заголовков после HERO: H2–H6, названий секций, карточек и кейсов;
- навигации;
- CTA;
- основного текста;
- интерфейсных подписей;
- дат, цен и чисел;
- латиницы;
- форм;
- статусов;
- пояснений и доказательств.

### 6.3. Типографический принцип

Главный контраст системы:

```text
экспрессивный кириллический display
+
спокойный и точный Onest для смысла и интерфейса
```

Display является композиционным знаком, но не должен ухудшать понимание продукта.

### 6.4. Общие правила

- Один экран или смысловой блок имеет одну главную типографическую доминанту.
- Крупный заголовок не заменяет ясную категорию продукта.
- Видимый H1 должен быть семантическим H1.
- Не использовать скрытый SEO-текст вместо нормальной категорийной строки.
- Line-height display проверяется оптически, особенно на кириллице.
- Основной текст получает комфортную длину строки.
- Кнопки и подписи не должны имитировать display ради декоративности.

## 7. Цветовая система

### 7.1. Core anchors

```css
:root {
  --abx-studio-purple: #ad95ee;
  --abx-studio-lime: #dde63f;
  --abx-studio-ink: #151716;
  --abx-studio-paper: #f3f4f0;
  --abx-studio-line: rgba(21, 23, 22, 0.14);
}
```

### 7.2. Роли

#### Purple — `#AD95EE`

- брендовый интерфейсный сигнал;
- навигационный акцент;
- выделение выбранного состояния;
- короткая смысловая маркировка;
- связь с основным коммерческим сайтом.

#### Lime — `#DDE63F`

- основное действие;
- активное состояние;
- короткий маркер;
- контрастная зона;
- небольшая функциональная подсветка.

#### Ink — `#151716`

- основной текст;
- тёмная поверхность;
- контрастная финальная зона;
- графические линии и структурные элементы.

#### Paper — `#F3F4F0`

- нейтральная студийная поверхность;
- фон, на котором реальные кейсы сохраняют собственные цвета;
- спокойная рабочая среда без SaaS-стерильности.

#### Line — `rgba(21,23,22,.14)`

- структурные границы;
- разделение данных;
- сеточные и интерфейсные линии;
- альтернатива тяжёлым теням.

### 7.3. Наследование цвета

Core-пара purple/lime не является обязательной заливкой каждого направления.

Направление может:

- сохранить оба цвета;
- оставить только один брендовый сигнал;
- использовать Core в шапке и footer, но создать отдельную палитру контента;
- заменить локальную палитру полностью;
- передать основной живой цвет реальным кейсам.

Направление обязано документировать роли собственных цветов. Простая замена purple на другой hue не считается самостоятельной арт-дирекцией.

### 7.4. Запрещено

- использовать purple и lime без определённой роли;
- превращать каждый элемент в акцентный;
- накладывать общий цветовой фильтр на реальные кейсы;
- вводить случайные дополнительные акценты;
- использовать dirty gradients;
- строить систему на декоративном glow;
- переносить локальную палитру одного направления на Studio Core.

## 8. Изображения, кейсы и материальность

### 8.1. Case-led принцип

Реальные кейсы являются главным доказательным, цветовым и композиционным материалом ANBOX.

Кейс должен:

- показывать уровень результата;
- объяснять вклад студии или продукта;
- сохранять собственный визуальный характер;
- появляться достаточно рано в сценарии;
- быть связанным с конкретным тезисом;
- работать на mobile без потери главного объекта.

### 8.2. Asset rules

- Упаковка, фото, видео, 3D и сложные изображения хранятся как заменяемые assets.
- Для заменяемых изображений использовать `img`, `picture`, `video` или явный `src`.
- Сложный визуал не рисуется CSS-ом, если это ухудшает заменяемость и качество.
- Важный текст не запекается в raster.
- Генеративные изображения не подменяют реальные результаты.
- Для точной упаковки, интерфейса или типографики использовать детерминированный мастер.
- Генеративное окружение и точный продуктовый мастер могут собираться раздельно.
- Все assets получают осмысленные `alt` или корректный декоративный статус.

### 8.3. Композиция

- Один сильный объект может определять всю секцию.
- Работы не обязаны помещаться в одинаковые карточки.
- Крупные crop разрешены, если главный объект остаётся понятным.
- Тактильный материал должен иметь смысл: бумага, фольга, стекло, печать, сгиб, экран, интерфейс.
- Декоративный материал не должен конкурировать с продуктом.

## 9. Брендовый уровень и шапка

Направление должно сохранять видимую связь с `ANBOX STUDIO`.

Возможные способы:

- бренд `ANBOX STUDIO` в шапке;
- подпись текущего направления;
- общая сетка;
- display + Onest;
- один core-акцент;
- общий footer;
- переходы между направлениями;
- общая логика CTA.

Требования:

- пользователь понимает, в каком направлении находится;
- категория продукта ясна без знания всей экосистемы;
- бренд студии не затмевает локальный продукт;
- направление не выглядит случайным отдельным проектом;
- шапка адаптируется, а не просто обрезается на mobile.

## 10. Компонентная логика

Core не задаёт одну обязательную форму каждой карточки. Он задаёт поведение компонентов.

### 10.1. CTA

- Ясно сообщает следующий шаг.
- Имеет стабильную кликабельную область.
- Основная подпись остаётся читаемой при motion.
- Не маскирует заявку под мгновенную покупку, если дальше следует личный диалог.
- На mobile не зависит от hover.
- Состояния focus, pressed, disabled и loading различимы.

### 10.2. Карточки

- Используются только при реальной необходимости группировки.
- Не становятся универсальным контейнером для каждой мысли.
- Могут иметь разную геометрию в разных направлениях.
- Не должны превращать сайт в SaaS-dashboard без продуктовой причины.

### 10.3. Кейсовые компоненты

- Главный кейс может быть крупнее остальных.
- Активная работа должна сохранять контекст серии.
- Mobile получает отдельную механику вместо симуляции desktop hover.
- Before/after имеет доступное управление и статичную альтернативу.

### 10.4. Навигация

- Показывает принадлежность к `ANBOX STUDIO`.
- Показывает активное направление или смысловой раздел.
- Не конкурирует с H1.
- Не скрывает важные пункты только за cursor interaction.
- На mobile превращается в понятное меню или touch-rail.

### 10.5. Формы

- Объясняют, что произойдёт после отправки.
- Имеют состояния validation, loading, success и error.
- Не показывают ложный успех до подтверждения записи.
- Содержат согласие и ссылку на политику, если это требуется.
- Не используют реальные клиентские данные для теста.

## 11. Motion

### 11.1. Принцип

Пользователь должен понять страницу без анимации. Motion добавляет причинно-следственную связь, характер материала, состояние или пространственную логику.

### 11.2. Motion budget

- Выбирать ограниченный набор согласованных эффектов.
- Не превращать страницу в демонстрацию всей библиотеки.
- Один уникальный эффект не требует общего 3D-движка.
- Переиспользуемый движок оправдан для нескольких сцен или проектов.
- Высокая интенсивность допустима в одной signature-зоне.
- В остальных разделах движение поддерживает ритм и иерархию.

### 11.3. Обязательные требования

- `prefers-reduced-motion`;
- статичное HTML/CSS-состояние;
- mobile-сценарий без hover;
- cleanup;
- обработка resize;
- остановка вне viewport;
- отсутствие блокировки критического текста;
- сохранение читаемости CTA;
- отсутствие деформации лиц, кейсов и продуктовых мастеров.

### 11.4. Производительность

```js
const pixelRatio = Math.min(window.devicePixelRatio || 1, 2);
```

- Canvas DPR обычно ограничивается значением `2`.
- Для запуска и остановки использовать `IntersectionObserver`.
- Scroll/touch listeners делать passive, если событие не отменяется.
- Тяжёлый canvas не загружать раньше критического текста.
- WebGL, видео и тяжёлая графика получают poster или облегчённый fallback.
- Финальную динамику проверять на реальном устройстве.

## 13. Tilda и VibeBlock

### 13.1. Scoped architecture

- Использовать уникальный root направления.
- Использовать собственный префикс классов.
- Не зависеть от глобальных селекторов Tilda.
- Не полагаться на глубокую DOM-вложенность.
- Предпочитать плоские классовые селекторы.

Пример:

```html
<section id="abx-study-root" class="abx-study">
  ...
</section>
```

```css
#abx-study-root .abx-study__title { ... }
#abx-study-root .abx-study__case { ... }
```

### 13.2. Публикация

- Проверять опубликованную версию, а не только редактор.
- После обновления использовать cache-busting параметр.

```text
https://example.com/page?nocache=TIMESTAMP
```

- Убедиться, что live-страница получила новый код.
- При многочастной поставке обновлять комплект целиком.
- Не смешивать части из разных версий.

### 13.3. Assets и CORS

- Canvas-assets, читаемые через `getImageData`, должны находиться на домене с корректным CORS.
- Для таких изображений использовать `crossOrigin="anonymous"` до загрузки.
- Обычные декоративные фото могут оставаться на CDN конструктора, если canvas не читает их пиксели.

## 14. Формы и end-to-end QA

Визуальное сообщение об успехе не считается успешной отправкой.

Проверяется весь путь:

```text
клик
→ validation
→ request
→ server response
→ запись
→ внешняя интеграция
→ уведомление
```

Проверить:

- обязательные поля;
- состояния ошибки;
- повторную отправку;
- CORS и preflight;
- фактическую запись заявки;
- Tilda «Заявки» или backend;
- email, Sheets или CRM;
- согласие и privacy;
- отсутствие реальных клиентских данных в тесте.
